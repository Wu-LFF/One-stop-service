## 📦 工具包概述

### 这是做什么的？

这个工具包包含一组 **Claude Code Skill**，每个 Skill 是一份结构化的 Markdown 指令文件，告诉 AI 如何完成一项特定的工作。你只需要在对话中说一句触发词，AI 就会按照 Skill 中定义的步骤一步步执行。

### 和项目工作法的关系

这套工具包是 `docs/项目工作法.md` 中方法论的 **可执行版本**。方法论讲"应该怎么做"，Skill 告诉 AI"具体怎么做"。两者配套使用：

```
方法论（道理）           Skill（工具）
─────────────           ────────────
先写文档再写代码    →    init-project 搭好骨架
文档要归类整理      →    organize-docs 自动归类
先做原型再开发      →    prototype-designer 生成方案
原型需要验证        →    validate-prototype 自动检查
```

### 三个核心原则

1. **先做一次，再固化**：每个 Skill 都先在实际工作中完整做一遍，确认流程正确，再写成指令
2. **步骤严格，产出可预期**：Skill 里的步骤 AI 不能跳过，确保每次输出质量一致
3. **持续迭代**：发现问题就改 Skill，积累经验就加 Skill，工具包会越来越强

## 📖 技能清单与能力说明

### 1. init-project —— 项目脚手架初始化

| 项目 | 说明 |
|------|------|
| **触发词** | `使用 init-project` / `/init-project` / `初始化项目` |
| **复杂度** | ⭐ 基础 |
| **前置条件** | 确认项目名称、技术栈、项目类型 |

**能力描述：**

生成标准化项目骨架，确保每个项目第一次提交时的结构是一致的。包括：

- 标准化目录结构（src、docs、tests、.claude、.vscode 等）
- CLAUDE.md —— 项目"宪法"，定义规范和约束 AI 行为
- .gitignore —— 根据技术栈生成对应的忽略规则
- .vscode/settings.json —— 统一的编辑器配置
- Git 初始化 + 首次提交

**典型输出：**

```
项目/
├── .claude/skills/          # Skill 目录，可把本工具包直接放进来
├── .vscode/settings.json    # 统一编辑器配置
├── docs/                    # 文档目录
├── src/                     # 源代码
├── tests/                   # 测试
├── .gitignore
├── README.md
├── CLAUDE.md                # 项目规范，AI 的"宪法"
└── package.json
```

### 2. organize-docs —— 文档自动归类

| 项目 | 说明 |
|------|------|
| **触发词** | `使用 organize-docs` / `/organize-docs` / `归类文档` |
| **复杂度** | ⭐ 基础 |
| **前置条件** | docs/ 目录存在，有松散文件 |

**能力描述：**

扫描 docs/ 根目录下的松散文件，按文件名特征自动归类到对应子目录。解决"文档越来越多，根目录越来越乱"的问题。

**归类规则：**

| 文件特征 | 归入目录 | 示例 |
|----------|----------|------|
| 含"蓝图""方案""规划"或 .docx | `01-蓝图方案/` | 园区蓝图规划.docx |
| 含"需求""流程""业务""功能"或 .xlsx/.csv | `02-业务需求/` | 人事功能清单.xlsx |
| 含"原型"或 .rp/.axure | `03-原型方案/` | 人事通原型.html |
| 含"PRD""产品需求" | `04-PRD/` | 人事通PRD.md |
| 图片 .png/.jpg/.gif | `02-业务需求/{模块}/` | 根据上下文判断模块归属 |
| PDF | `01-蓝图方案/` | 系统规划书.pdf |
| 无法识别 | 列出给用户确认 | — |

**效果示例：**

```
归类前：                        归类后：
docs/                          docs/
├── 人事通原型.html      →      ├── 03-原型方案/人事通原型.html
├── 需求清单.xlsx         →      ├── 02-业务需求/需求清单.xlsx
├── 蓝图规划.docx         →      ├── 01-蓝图方案/蓝图规划.docx
├── 已归档的/                   ├── 已归档的/
└── ...                         └── ...
```

### 3. prototype-designer —— 原型方案 + PRD 生成

| 项目 | 说明 |
|------|------|
| **触发词** | `使用 prototype-designer` / `/prototype-designer` / `开始原型` |
| **复杂度** | ⭐⭐⭐ 高级 |
| **前置条件** | 存在 `docs/requirements.md`，含功能模块定义 |

**能力描述：**

从需求文档出发，按模块引导用户确认业务流程、页面清单、核心字段、交互规则，然后生成两个交付物：

1. **原型方案文档** —— 每个页面的布局结构、核心元素、交互说明、数据字段
2. **PRD 文档** —— 包含功能范围、业务流程、页面规则、数据模型、非功能需求

**典型工作会话：**

```
你: 开始原型
AI: 读取需求文档... 找到 HR 人事模块，包含以下功能：
    1. 员工档案管理
    2. 入离职管理
    3. 考勤管理
    我们先从员工档案开始。这个模块的核心流程是怎样的？

你: 管理员可以查看所有员工档案，员工本人只能看自己的...

AI: 页面清单我理解有：列表页、详情页、编辑页。字段包括姓名、部门、岗位...
    还需要补充什么？

...（确认后 AI 输出原型方案文档）...

AI: 原型方案已完成，请确认。确认后我继续生成 PRD。
```

### 4. validate-prototype —— 原型断链验证

| 项目 | 说明 |
|------|------|
| **触发词** | `使用 validate-prototype` / `/validate-prototype` / `验证原型` |
| **复杂度** | ⭐⭐ 进阶 |
| **前置条件** | 存在 HTML 原型文件（三端结构） |

**能力描述：**

读取 HTML 原型文件，自动检查所有导航跳转是否正确。可以检测出：

- **断链** —— mNav() 调用的页面 ID 不存在
- **缺失页面** —— PC 端 data-pc 或门户 data-portal 指向的页面未定义
- **缺失函数** —— onclick 中调用的函数没有定义
- **重复 ID** —— 多个页面使用了相同的 ID

**校验范围：**

| 检查项 | 检测内容 | 严重程度 |
|--------|----------|----------|
| mNav 目标 | `mNav('mp-xxx')` → 是否有 `id="mp-xxx"` 的 m-page | 🔴 高 |
| data-pc 映射 | `data-pc="pc-xxx"` → 是否有 `id="pc-xxx"` 的 pc-page | 🔴 高 |
| data-portal 映射 | `data-portal="portal-xxx"` → 是否有对应的 portal-page | 🔴 高 |
| 函数定义 | onclick 调用的函数是否在 JS 中定义 | 🟡 中 |
| ID 重复 | 不同页面元素是否使用了相同的 ID | 🟡 中 |

**输出报告示例：**

```
✅ mNav 移动端导航: 16/16 通过
✅ data-pc PC 端导航: 12/12 通过
✅ data-portal 门户导航: 6/6 通过
✅ 函数定义: 18/18 通过
✅ ID 唯一性: 无重复
总体状态: ✅ 全部通过
```

## 💡 使用场景举例

### 场景一：启动一个新项目

```
1. 说 "初始化项目"          → AI 引导输入项目信息，生成骨架
2. 把 skills-pack 安装进来  → bash install.sh
3. 开始写需求文档            → 手动或 AI 辅助
4. 说 "归类文档"             → 自动把写好的文档归类到位
```

### 场景二：为一个新模块做原型

```
1. 在 requirements.md 添加模块描述
2. 说 "开始原型"            → AI 按模块引导确认需求
3. 确认原型方案             → AI 输出原型方案文档
4. 实现 HTML 原型           → 基于方案直接生成 HTML
5. 说 "验证原型"            → AI 自动检查所有导航跳转
```

### 场景三：接手一个已有项目

```
1. 说 "初始化项目"          → 补全缺少的目录和规范文件
2. 安装 skills-pack          → 所有技能直接可用
3. 说 "归类文档"             → 整理已有的散乱文档
4. 查看各 Skill 说明          → 了解 AI 能帮你做什么
```

## 🚀 安装方式

### 方式一：自动安装（推荐）

```bash
# 在目标项目的根目录下执行
bash path/to/skills-pack/src/install.sh
```

脚本会自动创建 `.claude/skills/` 目录，复制所有技能文件。已存在的技能会跳过。

### 方式二：手动安装

1. 在项目根目录创建 `.claude/skills/` 目录
2. 将 `src/.claude/skills/` 下的每个技能文件夹复制进去
3. 确认结构如下：

```
你的项目/
├── .claude/
│   └── skills/
│       ├── init-project/
│       │   └── SKILL.md
│       ├── organize-docs/
│       │   └── SKILL.md
│       ├── prototype-designer/
│       │   └── SKILL.md
│       └── validate-prototype/
│           └── SKILL.md
└── ...
```

## ✏️ 如何沉淀新技能

在项目推进过程中，遇到重复性工作就可以沉淀为新的 Skill。流程如下：

### 沉淀标准

满足以下条件之一，就值得写成 Skill：

- **AI 帮你做过两次的事** —— 如部署配置、代码审查、数据库迁移
- **有固定步骤的事** —— 如创建新模块、添加新 API、运行测试套件
- **容易出错的事** —— 如环境配置、数据迁移、权限设置
- **需要多人统一的事** —— 如代码风格检查、提交规范、发布流程

### 沉淀步骤

```
1. 先做一遍           → 确认流程是对的，步骤是完整的
2. 写成流程文档        → 记录每一步做什么、产出什么
3. 创建 SKILL.md       → 按 Skills 格式写成 AI 可执行的指令
4. 放到技能包          → 加入 docs/skills-pack/src/.claude/skills/{名称}/
5. 更新这个 README     → 在本文件的技能清单和变更记录中登记
6. 提交 Git            → 存档一版
```

### SKILL.md 模板

```markdown
---
name: {skill-name}
description: {一句话说明这个 Skill 做什么}
version: 1.0.0
---

# {Skill Name} — {中文名称}

{简要说明}

## 使用方式

在对话中输入 `使用 {skill-name}` 或 `/{skill-name}` 触发。

## 流程

按以下步骤顺序执行，不要跳过。

### 步骤 1：{步骤名}
{具体做啥}

### 步骤 2：{步骤名}
{具体做啥}

## 注意事项
- {特殊情况1}
- {特殊情况2}
```
