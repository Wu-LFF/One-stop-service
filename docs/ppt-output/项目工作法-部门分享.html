第一步：Agent 选择

为什么是 Claude Code？

Claude Code 的核心优势

Claude Code 不是一个"代码补全工具"，它是一个完整的软件开发 Agent——能够理解整个项目上下文、自主规划多步骤任务、直接操作文件系统、执行 shell 命令。

"能读懂整个项目，不是只补一行代码"——这是 Agent 和 Copilot 的本质区别。

关键差异：Claude Code 拥有 200K token 上下文窗口，能够一次性加载项目文档、架构设计、需求总纲，在"理解全局"的基础上做决策。它不是补全，是推理 + 执行。

Claude Code vs Trae 对比

维度Claude CodeTrae
定位全栈 Agent，自主规划+执行IDE 内置 AI 助手，侧重补全
上下文200K token，全项目感知受限于 IDE 上下文窗口
工具调用文件读写、shell、Git 全能力以代码建议和补全为主
CLAUDE.md项目级"宪法"，定义规范与工作流无对等项目规范机制
记忆系统四类持久化记忆，跨会话继承无持久化记忆能力
Skill 机制可打包复用技能，流程编码化无 Skill 机制

第二步：统一项目框架

init-project · 一键生成

为什么需要统一框架？

每个新项目从零搭建目录结构、手动写 CLAUDE.md、配置 CI/CD——这是重复劳动。更严重的是，不同项目的目录风格不一致，团队成员切换项目时需要重新适应。

统一框架 = 消除重复劳动 + 确保项目一致性 + 降低认知切换成本

标准化项目骨架包含：CLAUDE.md（项目宪法）、目录结构（docs/src/tests/scripts）、.gitignore、CI/CD 配置、编辑器配置。

跨项目复用方式

1

Skill 封装

将 init-project 封装为可复用 Skill，调用即生成

2

模板仓库

GitHub 维护模板仓库，新项目 clone → 替换项目名 → 开始开发

3

CLAUDE.md 作为契约

定义规范、索引文件、行为约束，AI 和人类共用同一份"宪法"

4

渐进增强

从最小骨架开始，随着项目推进逐步补充 docs/ 和 skills/

第三步：需求的根基地位

一切产出的前提
需求文档 = 问答助手的知识库。知识库不完整 → 答案必然偏。需求不完整 → 所有后续产出都会偏离。
01
为什么需求必须完整？
AI 的推理基于你给的信息。需求缺失 = AI 自己脑补 = 产出偏离预期。你在需求阶段省的时间，会在返工阶段十倍偿还。
02
需求包含什么？
项目简介（一句话说清做什么）、背景与痛点、可衡量目标、分阶段计划、功能模块清单、系统集成关系、非功能需求（性能/安全/兼容性）、变更记录。
03
需求确认前置法
用户提需求 → AI 反问 5 个关键问题（字段、类型、选项、跳转、取消）→ 用户确认 → 一次性生成。确认清单 = "口头 PRD"，后续可追溯。把最需要脑子的活放在脑子最清楚的时候干。

核心原则：需求文档不是"写一次就扔"的过场。它是项目的源头真相——架构设计基于它，原型方案基于它，测试用例基于它。

0517

延伸：功能级需求确认

有了需求文档还不够

为什么每个小功能还要确认？

项目需求文档定义了大方向——但具体到"一个编辑表单有哪些字段""下拉选项的数据来源""取消按钮跳转到哪"，这些细节文档覆盖不到。每个功能模块开始前，AI 必须先反问、确认细节、再一次性输出原型。

需求文档 = 地图。功能确认 = 每一步落脚前再看一眼路面。

先确认再输出 vs 先生成再修改

维度先确认再输出先生成再反复修改
准确性一次性命中，偏离小第一版大概率跑偏
Token 消耗确认对话 2-3 轮 + 生成 1 轮反复修改 5-10 轮，每轮重读文件
上下文健康干净上下文完成核心工作修改过程填满上下文 → 越改越歪
返工成本微调即可推倒重来的风险高

先生成再反复修改的恶性循环

1
上下文爆炸
每轮修改都产生新的对话历史 → 窗口快速填满 → AI 开始"忘记"前面的约束 → 后续修改越来越偏
2
方向漂移
AI 在第 5 轮修改时已丢失第 1 轮的需求细节 → 改 A 修好 B 又坏 C →"怎么越改问题越多"
3
Token 黑洞
10 轮修改 × 每轮重读整个 HTML 文件 → 几百 KB 上下文消耗 → 还没开始下一个模块，窗口已经紧张
0617

为什么先做小功能，再组合为大功能？

积木策略
1

上下文可控，不互相污染

小模块 = 需求少 = 确认快 = 会话短。每个小功能在一个干净上下文中完成，修改模块 A 不会影响模块 B 的上下文。

2

质量可验证，问题可隔离

小功能产出小，validate-prototype 快速校验。问题在小范围内发现和修复，不影响其他模块。不用"大海捞针"式排查。

3

commit 粒度合理，回退精准

每个小功能一个 commit。出问题 git revert 只回退一个小模块，不会牵连一片。Git log 本身就是模块化的演进叙事。

4

组合即交付，积木成厦

3 个小功能各自完成并通过验证 → 组合为一个完整模块 → push 到 GitHub。积木搭好了，拼起来就是大厦。不是"一步到位"，是"步步为营"。

←
反模式：大而全
一口气生成整个模块 → 需求不明确 → 上下文爆炸 → 反复修改 → 越改越偏 → 推倒重来
→
正模式：小而精
逐个确认 → 逐个生成 → 逐个验证 → 逐个 commit → 组合交付。每一步都在干净上下文中。
★
Token 效率对比
大而全：10+ 轮修改 × 重读文件 → 几百 KB 浪费。小而精：3 轮确认 + 1 轮生成 → 总共不到 50KB。

支柱一：Skill 沉淀机制

流程编码 · 可打包复用

什么是 Skill？

Skill 是把一套完整工作流程编码为可复用的指令文件。它包含：触发关键词、执行步骤、输入/输出格式、约束条件。调用一个 Skill = 让 AI 按照你定义好的流程执行任务。

核心逻辑：做一次 → 发现规律 → 沉淀为 Skill → 下次调用即用 → 持续优化迭代。Skill 是"流程的代码化"。

已有 Skills 示例

1

init-project

标准化项目脚手架一键生成

2

organize-docs

自动扫描 docs/ 并按四层体系归类

3

prototype-designer

需求→原型方案确认→PRD 文档输出

4

validate-prototype

自动化断链检查与验证报告

支柱二：文档自动归类

按模块不按类型

四层目录体系

01

蓝图方案/

原始蓝图、规划文档（只读归档，不修改）

02

业务需求/

按模块：HR人事 / 行政 / 生产 / 通用。每模块 README 导航

03

原型方案/

HTML 可交互原型 + 原型方案文档

04

PRD/

产品需求文档，经原型验证后产出

归类核心原则

按模块不按类型：HR 相关的需求、原型、PRD 放在一起，而不是所有需求文档堆在一起。这样查一个模块的所有产出在一个目录里就能看完。

不要把输出都堆在一起。新文件即刻归类，不堆积在根目录。organize-docs skill 可自动扫描并建议归类。

README 导航：每个模块目录放 README.md 作为导航入口，列出该模块的所有文档和它们之间的关系。

支柱三：记忆系统

跨会话持久化 · 四类记忆

核心问题：Claude Code 的每次会话是独立的。新会话 = AI 对你的项目、你的偏好、你之前的决策一无所知。记忆系统解决的就是"跨会话信息传递"。

user
用户角色与偏好
记录用户的角色、知识水平、协作偏好。让 AI 在新会话中直接用正确的方式与正确的人沟通，不需要每次重新自我介绍。
feedback
反馈纠正记录
记录"不要这样做""对就是这样"以及为什么。避免 AI 在后续会话中重复犯错，也避免忘记已验证有效的做法。
project
项目上下文
记录项目目标、当前任务、架构决策、Skill 使用情况。拆分会话后新会话能自动继承进度，不需要重新解释项目。

关键原则：只记机器无法推断的。代码规范、文件路径等项目本身可读取的内容不需要存入记忆。记忆要记的是人的决策、偏好、反馈和原因。MemORY.md 索引保持简洁（超 200 行会被截断），过时记忆及时更新或删除。

支柱四：版本仓库

Git + GitHub · 可回溯存档

为什么需要版本管理？

1

可回溯

任何时间点的代码状态都可以恢复。改错了 → git revert 找回。不需要靠"我记得之前是那样写的"。

2

双保险

本地 Git 存档 + GitHub 远程推送。电脑坏了、文件误删、目录搞乱了——远程仓库是最安全的备份。

3

演进日志

commit log = 项目的"航海日志"。什么时候做了什么、为什么做，一目了然。新人接手也能快速理解项目脉络。

GitHub 存档策略

本地

高频 commit

完成一个原子操作 → commit。不攒一堆改动一起提交。

远程

关键节点 push

每个模块完成、每个里程碑达成 → push 到 GitHub。不是每个 commit 都 push，但每次 push 都代表一个可交付状态。

规范

中文提交信息

"{动词}{名词} — {补充说明}"。提交信息本身就是项目文档。git log 就是项目的时间线叙事。

上下文窗口机制

满了会怎样？怎么破？

上下文窗口是什么？

每次对话中，AI 能"看到"的信息量是有上限的（Claude Code 为 200K token）。这包括：系统提示、CLAUDE.md、对话历史、文件读取结果、工具调用结果。所有内容都在一个窗口里。

200K token ≈ 一本《三体》的篇幅。单次会话里读太多文件、对话轮次太多、输出内容太长 → 窗口被填满。

窗口满了会发生什么？

后果具体表现
上下文压缩系统自动压缩早期对话 → 关键决策细节被"概括"丢失
内容跑偏AI 基于残缺上下文推理 → 输出偏离原定方向
重复劳动AI "忘记"已读过的文件，重新读取 → 浪费 token
质量下降简单操作出错（正则转义混乱、路径拼错、变量名混用）
输出崩溃极端情况下丢失核心约束，生成完全偏离规范的代码

根本问题

AI 不"知道"自己丢掉了什么信息。它看到的是压缩后的残缺上下文，但不会主动告诉你"前面的内容我已经忘了"。你看不出来它忘了，它自己也不知道自己忘了——这是最危险的。

上下文压缩不是"优雅降级"，是"静默破坏"。信息不是在最后一刻丢失的——是在你不知不觉中一点一点丢掉的。

四个预警信号

1

同一大文件被 AI 重复读取 3-4 次

2

简单操作连续出错（正则、路径拼接）

3

系统出现上下文压缩提示

4

对话超 15-20 轮或变更超 500 行

会话管理策略

commit 为界 · 记忆做桥
1
识别信号
出现任一预警信号：重复读取、连续出错、压缩提示、超 15 轮
→
2
立即 Commit
把所有当前变更提交为一个有意义的 commit
→
3
写入记忆
把当前进度、决策、待办写入 memory 系统
→
4
新开会话
开启全新会话，memory 自动加载上下文继承
→
5
继续推进
干净上下文 + 清晰目标 = 高效推进

核心策略：commit 即分界。每次 commit 后评估是否需要新开会话。memory 做桥梁，新会话自动继承进度。不要在同一个会话里硬撑——上下文不会自己恢复。

Commit 的节奏与版本策略

什么时候 commit？什么时候 push？

6 个必须 Commit 的节点

1

项目初始化完成

init-project 生成骨架 + CLAUDE.md → 第一个 commit，项目诞生

2

需求/架构文档确定

requirements.md + architecture.md 完成 → 锁定"源头真相"

3

文档归类完成

docs/ 目录结构调整 → commit 记录目录变化

4

新增或更新 Skill

skill 目录和 skill.md → 技能沉淀落库

5

原型方案产出

HTML 原型 + .md 方案文档 → 交付物落库

6

功能代码实现

功能代码 + 测试 → 可运行状态落库

Push 到 GitHub 的时机

不是每个 commit 都 push。Push = "这个状态值得在远程留底"。

模

模块完成时 push

一个功能模块开发完成且自测通过 → push。代表一个可追溯的交付节点。

碑

里程碑达成时 push

版本号升级（v1.0 → v1.2）、重大架构调整完成 → push + tag 标记。

险

风险操作前 push

大规模重构、删除文件、实验性改动之前 → 先 push 当前状态。万一搞砸了，远程有安全基线。

日

每日收工时 push

一天工作结束，代码处于可编译/可运行状态 → push。第二天换个电脑也能继续。

经验沉淀与持续输出

从实践到方法论
写
文档化每一次实践
每完成一个模块，写一份简短的复盘文档：做了什么、遇到了什么问题、怎么解决的、有什么可复用的。这些文档是团队最宝贵的资产——比代码本身更有长期价值。
编
编码化为 Skill
发现一个可复用的流程 → 写成 Skill。触发关键词 → 执行步骤 → 输出格式。一次实践 → 永久复用。Skill 是"流程的代码化"，是经验的硬载体。
讲
部门分享与培训
定期做内部分享（就像今天这样）。把你学到的东西讲给别人听——教学是最高效的学习方式。幻灯片、演示文稿本身就是输出产物。
"一个项目做完了，留下的不应该只有代码。应该留下：可复用的 Skill、可参考的文档、可追溯的 Git 记录、可继承的记忆。这些才是团队的复利资产。"

输出的形态

1

项目文档（需求/架构/PRD）

2

可复用 Skill（.md 指令文件）

3

演示文稿（内部培训用）

沉淀的载体

4

Git commit log（演进叙事）

5

Memory 记忆系统（跨会话上下文）

6

CLAUDE.md（项目宪法，持续迭代）
