为什么需要这套方法论

传统做法，哪里不够？

这些问题你是否也遇到过？

💬 需求"说着说着就变了"

口头沟通的需求没有统一记录，开发到一半才发现理解不一致。文档和代码各写各的，没人知道哪个是准的。

🎨 原型做好了，没法自动检查

用 Axure/Figma 画的原型是图片，没法做自动化校验。有没有页面断链、跳转对不对，全靠肉眼过。

🔄 重复工作每次都重来

项目结构搭建、文档分类、原型验证……这些工作每个项目都要做一遍，没人沉淀成可复用的工具。

🧠 AI 聊完就忘

和AI协作时，会话一压缩或一关，之前的约定和上下文全丢了。每次都要重新交代一遍背景。

方法论基石

五个核心原则

这五个原则贯穿项目始终，是后面所有方法的基石

📋

文档驱动

先写文档，再写代码。文档不是"写完就扔"的产物，而是开发过程中持续依赖的"唯一事实来源"。

🎨

原型验证

写代码之前先用可交互HTML原型跑通流程。发现问题在原型阶段改，比改代码成本低10倍。

⚙️

技能固化

重复性工作（搭建项目、归类文档、检查原型）写成AI Skill。下次再做，一键执行，不出错。

📈

渐进交付

不追求一步到位。分模块、分阶段推进：先试点一个模块，验证可行再推广，逐步覆盖全部功能。

🔖

版本对应

文档、原型、代码全部纳入Git管理。每次变更提交一个记录，整个项目的历史一目了然。

工作流程

八步工作流

每一步都产出明确的交付物，每一步都是下一步的输入

1 需求文档 把业务想法写成结构化文档，明确功能范围和优先级 📄 requirements.md
2 架构设计 确定技术选型、模块划分和系统分层 🏗️ architecture.md
3 文档归类 按业务模块建立清晰的目录结构 📂 docs/ 结构化
4 原型设计 制作三端（手机/PC/门户）可交互HTML原型 🎨 原型.html
5 原型验证 自动化检查所有页面跳转和交互，零断链 🔍 validate-prototype
6 技能固化 把可重复的流程编码为 AI Skill ⚙️ .claude/skills/
7 代码开发 在有文档、有原型、有验证机制的基础上写代码 💻 实现
8 Git 提交 每次变更对应一个提交，演进历史可追溯 🔖 git commit
第1步

文档驱动 —— 先写文档，再写代码

文档不是"写完了就归档"的产物，而是整个项目开发过程中持续依赖的"可执行需求"

📄 requirements.md

需求总纲

项目背景、痛点、目标、功能模块清单（含优先级 P0/P1/P2）、系统集成关系、非功能需求。

🏗️ architecture.md

架构设计

技术选型、分层架构图、模块划分、接口协议、主数据管理。确保团队对系统结构有一致的理解。

📜 CLAUDE.md

项目规范（AI"宪法"）

定义代码规范、工作流、目录结构、约束条件。让AI在协助开发时始终遵循统一规则。

✗ 没有文档驱动的问题

  • 需求在微信/邮件里，找起来非常困难
  • 开发做着做着发现方向偏了
  • 新成员加入要口述一遍所有背景
  • 同一个功能不同人的理解不一样

✓ 文档驱动的好处

  • 团队所有人对需求的理解一致
  • 每次变更都在文档上先改，再讨论
  • 新成员自己看文档就能上手
  • 需求、架构、代码三者版本对应
第2步

原型先行 —— 写代码前先验证方案

用 HTML 制作可交互原型，三端合一（手机端 + PC 端 + 管理门户），浏览器直接运行

📱
手机端
m-page · mNav()
💻
PC 端
pc-page · data-pc
🔐
管理门户
portal-page · data-portal

🔄 原型做完了，还能自动检查

validate-prototype 会自动扫描整个原型文件，检查所有页面跳转是否有对应的目标页面、所有被调用的函数是否正确定义、是否有重复的页面 ID。结果立即可见。

✗ 传统工具（Axure / Figma）

  • 需要安装专门软件
  • 原型是"图片"，无法做自动化检查
  • 不能放进 Git 做版本对比
  • 分享需要部署或导出
  • 断链只能人工逐个点

✓ HTML 原型

  • 浏览器直接打开即可运行
  • 可做自动化断链、函数、ID检查
  • Git 管理可 diff 可追溯
  • 分享一个文件或链接即可
  • 20个页面断链检查只需几秒
方法论

需求确认前置 —— 脑子最清楚时做最重要的决策

会话初期原型往往只需微调；越到后面越不准。这不是AI变笨，是信息衰减

❌ 常见反模式：边做边改

用户：帮我做个编辑页面
AI 直接生成 → 字段少了 → 补充 → 再加 → 样式不对 → 再改
→ 10+ 轮迭代 → 上下文膨胀 → 质量断崖

✅ 正确做法：先确认，再生成

1. 用户提需求 → AI 反问确认（字段/类型/选项/跳转）
2. 用户逐项确认 → 形成"口头 PRD"
3. AI 一次性生成完整原型
→ 1-2轮微调即完成

📋 问答式确认模板

🔹 需要哪些字段？名称、类型、默认值
🔹 每个字段的类型？文本/下拉/数字/日期
🔹 下拉选项有哪些？逐项列出
🔹 保存后跳转到哪？返回列表/留在当前
🔹 是否需要取消按钮？点击行为是什么

🔗 与上下文管理的配合

• 确认在会话初期（上下文最干净时）完成
• 生成后立即 commit，复杂模块新开会话
把最需要脑子的活，放在脑子最清楚的时候干
第3步

技能固化 —— 把重复工作变成"一键执行"

Skill 是把一个完整的工作流程（步骤+规范+产出物）编码为 AI 可以严格遵循的指令集

🚀

init-project

一键生成标准化项目骨架：目录结构、CLAUDE.md、配置文件

📂

organize-docs

自动扫描 docs/ 目录，把新文件按模块归类到正确位置

🎨

prototype-designer

从需求文档自动生成原型方案和 PRD，按步骤确认

🔍

validate-prototype

检查 HTML 原型的所有导航跳转、函数定义、ID 重复

💡 Skill 的核心价值： 先做一次确认流程是对的 → 做第二次时把它写成 Skill → 以后每次都一键执行
第4步

记忆系统 —— 让 AI 拥有长期记忆

AI 会话压缩后，关键上下文不会丢失。这是"AI 越用越懂你"的核心

👤

user 用户信息

你的角色、技术背景、偏好。比如：你是后端转前端，不懂 React hooks —— AI 就不会用高级 React 概念解释问题

💡

feedback 反馈

你纠正过 AI 什么、肯定了 AI 什么。比如："不要每次问我权限了" → 自动生成权限配置

📌

project 项目

项目目标、当前状态、关键决策、截止时间。AI 知道项目进行到哪一步了

🔗

reference 参考

外部系统位置、文档索引、工具地址。比如：Bug 在 Linear 的 INGEST 项目里跟踪

📂 记忆文件结构

.claude/projects/{hash}/memory/
├── MEMORY.md ← 索引（始终加载）
├── about-user.md
├── project-overview.md
├── feedback-*.md
└── reference-*.md

效果：AI 不再是"每次都从零认识你"。重启对话后，它还记得你的偏好、项目进展、之前踩过的坑。这就相当于每个项目都有一个"了解全部上下文"的 AI 助手。

第5步

上下文窗口管理 —— 别让 AI "偷偷失忆"

上下文满了会被自动压缩，AI 不告诉你"我忘了"——它只会悄悄出错

⚠ 上下文满了会怎样

🔴 信息丢失 — 压缩后的摘要丢失中间讨论细节
🟠 重复劳动 — AI 重新读取读过的文件
🟡 简单操作出错 — 正则混乱、改错位置
🔵 质量下降 — 丢失约束，偏离规范

✅ CLAUDE.md 减负效果

砍掉三类：通用知识 / 空占位 / 冗余指令
保留四类：项目定位 / 行为约束 / 文件索引 / 特殊约定
本项目：30行 → 13行（-57%），每次会话省 ~200 token

🔄 会话拆分策略

📏 粒度：一个 commit = 一个会话
🚩 拆分信号：
• 同一文件被重复读取 3-4 次
• 简单操作（正则/路径）连续出错
• 对话 > 15-20 轮或变更 > 500 行

📄 HTML/PPT 特别注意

• HTML 原型（1000+行三端合一）：编辑优先用 grep/sed，批量用脚本，验证独立会话
• PPT 文件：AI 不能直接编辑 .pptx，需人工同步；等 .md 稳定后统一导出
核心：commit 即分界，memory 做桥梁
第6步

版本管理 —— 文档和代码一起版本化

不只是代码需要 Git 管理，文档、原型、配置都纳入版本控制，形成完整的项目演进历史

📝 一条好的提交信息

使用中文，格式：「做什么事 — 补充说明」

✓ 新增人事通原型 V1.0 — 三端完整交互原型
✓ 初始化项目结构 — 骨架目录 + .gitignore
✓ 存档项目工作法 HTML 演示文稿及相关产物
✗ feat: update prototype
✗ fix bug

🔖 什么东西要提交？

📄 requirements.md 🏗️ architecture.md 📂 docs/ 目录结构 🎨 原型文件 .html ⚙️ Skills/ 🧠 memory/ 记忆 📜 CLAUDE.md 💻 源代码 🧪 测试用例 🔧 配置文件

💡 为什么文档也要版本化管理？

因为文档和代码是"同步演进"的。需求变了 → 先改文档 → 再改代码 → 一起提交。这样任何时候回头看，都知道"当时为什么要这么改"。

价值对比

用了这套方法，有什么区别？

不是颠覆性的改变，而是每个环节都"多做了一点点"，但合起来效果显著

✗ 传统方式

  • 需求在口头/微信里，找起来靠问
  • 文档写一次就归档，开发和需求脱节
  • 原型用 Axure/图片，没法自动化检查
  • 重复工作每次重新做一遍
  • AI 聊完就忘，每次重新交代
  • Git 只有代码，看不出为什么改
  • 项目交接要花大量时间讲上下文

✓ 这套方法

  • 需求在文档里，所有人看到的一致
  • 文档是开发依据，随需求持续更新
  • HTML 原型可交互、可自动校验
  • 重复工作写成 Skill，一键执行
  • 记忆系统让 AI 记住项目上下文
  • Git 包含文档+原型+代码，历史完整
  • 新成员看文档+记忆系统就了解全局
行动指南

如何开始使用这套方法？

不用一步到位，从最简单的入手，逐步建立习惯

1

先写一份 CLAUDE.md

这是投入最小的第一步。只需要记录项目名称、技术栈、基本规范。下次 AI 辅助时就会自动遵守这些规则。

2

下一个需求，先写文档再做原型

不要急着写代码。先花 30 分钟写个简单的需求文档，再做一份 HTML 原型。你会发现在这个阶段改方案的成本几乎为零。

3

遇到重复工作，就沉淀一个 Skill

当 AI 帮你做完某件事两次时，就把它写成 Skill。下次再说"用 xxx skill 做"就全自动完成了。积累越多，效率越高。

4

把重要的上下文写进记忆系统

当 AI 问过你某个问题两次以上，或者你纠正过 AI 同一个错误两次，就把它记下来。Session 压缩后，记忆还在。
