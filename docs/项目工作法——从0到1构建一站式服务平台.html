第一步：项目初始化

init-project

产物目录结构

  • CLAUDE.md — 项目"宪法"，定义规范与工作流
  • .gitignore — 忽略规则（node_modules / .env / dist）
  • .github/workflows/ — CI/CD 流水线配置
  • .vscode/ — 编辑器统一配置
  • docs/ — 文档目录（初始为空，逐步填充）
  • src/ · tests/ · scripts/ — 源码/测试/脚本

为什么这样做

  • 问题：每个新项目从零搭目录 → 标准化模板一键生成
  • 问题：团队/AI不知道规范 → CLAUDE.md就是"宪法"
  • 问题：不同项目风格各异 → .vscode/ + .github/ 统一
  • 核心价值：消除重复劳动，确保所有项目一致性

第二步：需求总纲与架构设计

requirements + architecture

requirements.md — 需求总纲

  • 项目简介 — 一句话说清做什么
  • 项目背景 — 为什么要做，现状痛点
  • 项目目标 — 可衡量（覆盖7000人、90%线上化）
  • 分阶段目标 — 试点→推广→全覆盖三步走
  • 功能模块 — 按优先级列出功能清单
  • 系统集成关系 — 对接哪些外部系统
  • 非功能需求 — 性能/安全/兼容性/可用性
  • 变更记录 — 版本+日期+变更内容

architecture.md — 架构设计

  • 技术选型 — 前端/后端/数据库/部署
  • 分层架构 — 接入层→应用层→流程层→集成层
  • 模块划分 — 各模块职责与交互关系
  • 设计原则 — 架构决策的判断依据
  • 主数据管理 — 数据来源和同步方式
  • ADR决策记录 — 重大决策背景与权衡
  • 实施路线 — 时间线规划与里程碑

第三步：文档归类管理

organize-docs

四层目录结构

  • 01-蓝图方案/ — 原始蓝图、规划文档（只读归档）
  • 02-业务需求/ — 按模块：HR人事 / 行政 / 生产 / 通用
    每个模块目录放 README.md 作为导航入口
  • 03-原型方案/ — HTML 可交互原型 + 原型方案文档
  • 04-PRD/ — 待产出的产品需求文档

归类核心原则

  • 按模块不按类型 — 按HR/行政/生产分类而非文件格式
  • README 导航 — 每个模块目录放README.md入口
  • 归类即整理 — 新文件立刻归类，不堆积在根目录
  • 可自动化 — organize-docs skill 扫描并建议归类

第四步：原型设计与验证

prototype-designer

三端合一 HTML 架构

  • 手机端 — 底部导航 + mNav() 页面切换
  • PC端 — 左侧导航 + 面包屑 + data-pc 绑定
  • 管理门户 — 左侧导航 + data-portal 绑定
  • ID规范 — mp-{模块} / pc-{模块} / portal-{模块}
  • 视图切换器 — 一键切换手机/电脑/门户

为什么用 HTML 原型

  • 零依赖 — 浏览器直接运行，无需装软件
  • 可自动化验证 — validate-prototype 做断链检查
  • 可Git追溯 — 提交版本控制，每次修改可diff
  • 可分享 — 一个链接远程团队即可预览
  • 核心差异：自动化质量门禁 — Axure/Figma做不到

需求确认前置法

关键方法

现象

越到后面
原型越不准

会话初期上下文干净→原型准确；后期信息压缩→越改越歪

方法

AI 先反问
再一次性生成

用户提需求 → AI反问5个问题（字段/类型/选项/跳转/取消）→ 用户确认 → 一次性生成完整原型

效果

10轮迭代
→ 1-2轮微调

确认清单="口头PRD"，后续可追溯，大幅降低上下文消耗

Skill 设计规范

触发关键词 → 流程步骤（不要跳过）→ 输出格式模板。先有流程，后有Skill：做一次→沉淀→编码固化。Skill纳入Git管理。

配合上下文管理

需求确认前置+会话拆分：确认→生成→commit，新开会话做下一个模块。把最需要脑子的活放在脑子最清楚的时候干。

第六步：记忆系统

四类记忆

user

用户角色与偏好

保存用户角色、知识水平、协作偏好。确保AI用正确的方式与正确的人沟通。

feedback

反馈纠正记录

记录"不要这样""对就是这样"，保存原因。避免AI重复犯错，也避免忘记已确认的好做法。

project

项目上下文

项目目标、当前任务、架构决策。拆分会话后新会话能自动继承进度。

reference

外部资源索引

外部系统位置、文档链接等。记住"去哪找"而非内容本身。

原则

只记机器无法推断的

代码规范、文件路径等项目本身可读取的不需要存。feedback要记"为什么"。

维护

信息变化时及时更新

MEMORY.md索引超200行被截断，保持条目简洁。过时记忆及时删除。

第七步：CLAUDE.md 减负策略

常驻上下文精炼

砍掉三类冗余

  • 通用知识：工作流图表、开发流程 — AI训练数据已包含，不需每次重申
  • 空占位：<!-- TODO: 补充 --> — 零信息量，纯占token
  • 冗余指令："遵循架构约束"+"阅读架构文档" → 前者已被后者隐含

保留四类必须

  • 项目定位 — 一句话说清项目是什么
  • 行为约束 — "提交信息使用中文"
  • 文件索引 — "功能实现前阅读 docs/xxx.md"
  • 特殊约定 — "新增方法时同步更新项目工作法"
  • 效果：本项目 CLAUDE.md 从 30行 → 13行（-57%），每次新会话节省约 200 token

四个预警信号

出现任一就该收手

同一大文件被AI重复读取 3-4 次

严重

简单操作连续出错（正则、路径拼接）

严重

系统出现上下文压缩提示

严重

对话超 15-20 轮或变更超 500 行

重要

核心策略：commit 即分界 — 每次 commit 后评估是否新开会话。memory 做桥梁，新会话自动继承进度。

上下文压缩：不是优雅降级，是静默破坏

警醒
后果具体表现真实案例
信息丢失压缩后摘要丢失中间讨论细节，AI "忘记"已确认方案—
重复劳动AI 重新读取已读过的文件，浪费 token 和时间同一HTML被反复Read 4-5次
简单操作出错正则转义混乱、改错文件位置、变量名混用门户端编辑时Node正则连续报错
产出质量下降丢失约束条件，生成代码偏离已确认规范编辑表单字段与弹窗不一致

根因：AI不"知道"自己丢掉了什么信息。它看到的是压缩后的残缺上下文，但不会主动告诉你"我忘了"。
