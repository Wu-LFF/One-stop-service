## 1. 总体工作流

```
需求文档 (requirements.md)
    │
    ▼
架构设计 (architecture.md)
    │
    ▼
文档归类 (organize-docs)  →  按模块拆分业务需求
    │
    ▼
原型设计 (prototype-designer)  →  HTML可交互原型
    │
    ▼
原型验证 (validate-prototype)  →  自动化断链检查
    │
    ▼
Skills固化  →  将流程编码为可复用的skill
    │
    ▼
代码开发  →  按需求文档实现
    │
    ▼
Git提交  →  版本对应关系记录
```

**核心原则**：先文档、再原型、后代码。每一步的产出是下一步的输入。

## 2. 第一步：项目初始化

### 2.1 目标

搭建标准化的项目骨架，确保所有项目有一致的目录结构、规范和工具配置。

### 2.2 产物

```
One-stop_service/
├── CLAUDE.md              # 项目级 AI 指令（定义规范、工作流）
├── README.md              # 项目简介
├── .gitignore             # 忽略规则
├── .github/workflows/     # CI/CD 流水线
├── .vscode/               # 编辑器配置
├── docs/                  # 文档目录（初始为空）
├── src/                   # 源代码（初始为空）
├── tests/                 # 测试（初始为空）
├── scripts/               # 工具脚本
└── .claude/               # AI 配置和 Skills
```

### 2.3 关键操作

1. 用 `init-project` skill 生成骨架
2. 在 `CLAUDE.md` 中定义：
   - 项目概览（一句话说清项目是什么）
   - 开发规范（文档先行、提交规范等）
   - 工作流（修改需求 → 告诉AI实现 → 提交代码）

### 2.4 为什么这么做

| 问题 | 方案 |
|------|------|
| 每个新项目都从零搭目录 | 标准化模板一键生成 |
| 团队成员/AI不知道规范 | `CLAUDE.md` 就是"宪法" |
| 不同项目风格各异 | `.vscode/` + `.github/` 统一配置 |

## 3. 第二步：需求梳理与架构设计

### 3.1 目标

将用户脑中的业务想法转化为结构化的文档，作为后续所有工作的唯一依据。

### 3.2 核心文档

#### `docs/requirements.md` — 需求总纲

包含：
- **项目简介**：一句话说清做什么
- **项目背景**：为什么要做，现状痛点是什么
- **项目目标**：可衡量的目标（如"覆盖7000人、90%业务线上化"）
- **技术架构**：选型依据和关键约束
- **分阶段目标**：试点→推广→全覆盖三步走
- **功能模块**：按模块列出功能清单（含优先级）
- **系统集成关系**：对接哪些外部系统、什么方式
- **非功能需求**：性能、安全、兼容性、可用性、易用性
- **变更记录**：版本+日期+变更内容

#### `docs/architecture.md` — 架构设计

包含：
- **技术选型**：前端/后端/数据库/部署
- **系统架构图**：分层架构（接入层→应用层→流程层→集成层）
- **模块划分**：模块职责和交互关系
- **设计原则**：架构决策的依据
- **主数据管理**：数据来源和同步方式
- **决策记录 (ADR)**：重大决策的背景和权衡
- **实施路线**：时间线规划

### 3.3 方法论要点

1. **背景要真实**：痛点写得越具体，后续设计越有针对性
2. **范围要收敛**：分阶段目标防止范围蔓延
3. **模块化拆分**：按业务领域（人事/行政/生产/通用）拆分，每个模块独立文档
4. **变更可追溯**：变更记录表让文档"活"起来

## 4. 第三步：文档归类管理

### 4.1 目标

随着项目推进，`docs/` 目录会积累大量文件（蓝图的 .docx、需求 .md、表格 .xlsx、表单模板 .doc），必须建立清晰的归类体系。

### 4.2 目录结构

```
docs/
├── requirements.md          # 需求总纲（顶层入口）
├── architecture.md          # 架构设计（顶层入口）
├── decisions/               # 架构决策记录
│
├── 01-蓝图方案/             # 原始蓝图、规划文档（只读归档）
│   └── 蓝图方案V0.5.docx
│
├── 02-业务需求/             # 按模块拆分的具体需求
│   ├── HR人事模块/          #   人事通
│   │   ├── README.md        #     模块概览
│   │   ├── 考勤查询.md      #     单个功能点
│   │   ├── 请假.md
│   │   ├── 调动.md
│   │   └── 表单模板/        #     原始表单附件
│   ├── 行政模块/
│   │   ├── README.md
│   │   ├── 住宿申请.md
│   │   └── ...
│   ├── 生产模块/
│   └── 通用模块/
│
├── 03-原型方案/             # HTML可交互原型 + 原型文档
│   ├── 人事通.html
│   └── 人事通.md
│
└── 04-PRD/                  # (待产出) PRD 文档
```

### 4.3 归类规则

| 文件特征 | 目标目录 |
|----------|----------|
| 含"蓝图""方案"或 .docx 且非需求 | `01-蓝图方案/` |
| 含"需求""流程"或 .xlsx/.csv | `02-业务需求/` + 对应模块 |
| 含"原型"或 .html | `03-原型方案/` |
| PRD 文档 | `04-PRD/` |

### 4.4 方法论要点

1. **按模块不按类型**：业务需求按「模块」（HR/行政/生产）分类，而非按「文件类型」
2. **README 导航**：每个模块目录放 `README.md` 作为入口，方便快速了解模块全貌
3. **归类即整理**：新文件进入项目后立刻归类，不堆积到 docs/ 根目录
4. **可自动化**：用 `organize-docs` skill 自动扫描并建议归类

## 5. 第四步：原型设计与验证

### 5.1 目标

在写代码之前，先用可交互原型验证产品方案，降低返工成本。

### 5.2 原型设计流程（prototype-designer）

```
读取需求文档
    │
    ▼
按模块确认（业务流程 → 页面清单 → 核心字段 → 交互规则）
    │
    ▼
输出原型方案（.md）
    │
    ▼
用户确认
    │
    ▼
输出PRD文档
    │
    ▼
汇总索引（SUMMARY.md）
```

**关键方法**：每次只聚焦一个模块，用户确认后再进入下一个。

### 5.3 HTML 原型规范

我们的原型是三端合一的 HTML 文件（手机端 + PC 端 + 管理门户）：

```
┌─────────────────────────────────────────────┐
│  视图切换器（手机/电脑/门户）               │
├──────────┬──────────────────┬───────────────┤
│ 手机端   │  PC 端           │  管理门户     │
│ (m-page) │  (pc-page)       │  (portal-page)│
│          │                  │               │
│ 底部导航 │  左侧导航        │  左侧导航     │
│ 页面内容 │  面包屑+内容区   │  顶部+内容区  │
└──────────┴──────────────────┴───────────────┘
```

**ID 命名规范**：
- 手机端页面：`mp-{模块名}`（如 `mp-reissue`、`mp-leave-approve`）
- PC 端页面：`pc-{模块名}`（如 `pc-att-query`、`pc-salary-confirm`）
- 门户页面：`portal-{模块名}`（如 `portal-employee`、`portal-approve`）

**导航机制**：
- 手机端：`mNav('page-id')` 函数
- PC 端：`data-pc` 属性绑定
- 门户：`data-portal` 属性绑定

### 5.4 原型验证流程（validate-prototype）

```
读取 HTML 文件
    │
    ▼
提取三类页面定义（m-page / pc-page / portal-page）
    │
    ▼
提取四类导航引用（mNav调用 / data-pc / data-portal / onclick函数）
    │
    ▼
逐项校验：
  ├─ mNav 目标是否存在?
  ├─ data-pc 目标是否存在?
  ├─ data-portal 目标是否存在?
  ├─ onclick 函数是否定义?
  └─ 页面ID是否重复?
    │
    ▼
输出验证报告
```

### 5.5 为什么用 HTML 原型而非 Axure/Figma

| 工具 | 优势 | 劣势 |
|------|------|------|
| Axure/Figma | 视觉设计强 | 需专门软件、无法自动化校验 |
| **HTML 原型** | 浏览器直接运行、可自动化断链检查、可提交 Git 做 diff、可分享链接 | 视觉精细度稍弱 |

**核心差异**：HTML 原型可以用 `validate-prototype` 做**自动化质量门禁**，这是 Axure/Figma 做不到的。

### 5.6 需求确认前置：问答式细化法

#### 现象：越到后面，原型越不准

在本次项目中观察到一个规律：

> **会话初期生成的原型往往比较符合需求，只需小调整；越到后面，AI 产出越偏离预期。**

这不是 AI 能力问题，而是**信息衰减**：会话刚开始时上下文干净，需求描述清晰聚焦；随着对话推进，历史信息被压缩，早前确认的细节可能丢失，导致后期修改越改越歪。

| 阶段 | 上下文状态 | 产出质量 |
|------|-----------|----------|
| 会话初期 | 上下文干净，需求信息密度高 | 原型准确，微调即可 |
| 会话中期 | 上下文积累，信息开始稀释 | 需反复提醒已确认的约束 |
| 会话后期 | 上下文压缩，细节丢失 | 简单操作出错，偏离早期规范 |

#### 解决方法：需求确认前置

**核心原则**：把确认工作集中到会话初期完成，而不是边做边确认。

**操作流程**：

```
用户提出需求
    │
    ▼
AI 不急着做，先"反问确认" ── 逐条核对字段、选项、交互规则
    │
    ▼
用户逐项确认（或纠正）
    │
    ▼
确认清单完善后，AI 一次性生成完整原型
    │
    ▼
微调（通常只需 1-2 轮）
    │
    ▼
commit 保存，需要大改动时新开会话
```

**反例**（不推荐）：

```
用户：帮我做一个编辑页面
AI：（直接生成）→ 字段少了 → 用户补充 → AI再加 → 样式不对 → AI再改
→ 来来回回 10+ 轮 → 上下文膨胀 → 质量下降
```

#### 问答式确认的实操模板

以行政通"巡更路线编辑"为例，AI 应先反问：

```
1. 编辑页需要哪些字段？
   → 路线名称、覆盖区域、安保员、巡查时段、备注

2. 每个字段的类型？
   → 名称=文本、区域=文本、安保员=下拉选择、时段=文本、备注=多行文本

3. 下拉选项有哪些？
   → 陈强、刘明、赵刚

4. 保存后跳转回哪里？
   → 返回巡更配置列表

5. 是否需要"取消"按钮？
   → 需要，点击不保存直接返回
```

**确认完成后**，AI 再一次性生成原型。这样一来，第一版通常就接近终稿，后续只需微调。

#### 为什么这个方法有效

1. **信息在上下文最干净的时候被固化**：需求确认在会话初期完成，不受后续信息稀释影响
2. **减少迭代轮次**：10 轮微调 → 1-2 轮微调，大幅降低上下文消耗
3. **可追溯**：确认过的清单就是"口头 PRD"，后续出错可以回溯
4. **配合会话拆分**：一个模块确认 → 生成 → commit，然后新开会话做下一个模块

#### 与上下文管理的关系

本方法与 [第七步：上下文窗口管理](#8-第七步上下文窗口管理与会话拆分) 互为补充：

| 策略 | 解决什么问题 |
|------|-------------|
| 需求确认前置 | 在上下文最干净时锁定需求，减少迭代 |
| 会话拆分 | 需求确认后尽快 commit，新开会话做下一模块 |
| CLAUDE.md 减负 | 让常驻上下文更精炼，给需求确认留出空间 |

> **一句话**：把最需要脑子的活（需求确认）放在脑子最清楚的时候（会话初期）干。

## 6. 第五步：Skills 技能固化

### 6.1 目标

将重复性工作流程编码为可复用的 Skill，下次做类似工作直接调用。

### 6.2 Skills 目录结构

```
.claude/skills/
├── init-project/           # 项目脚手架生成
│   └── skill.md
├── organize-docs/          # 文档自动归类
│   └── skill.md
├── prototype-designer/     # 原型与PRD生成
│   └── skill.md
└── validate-prototype/     # 原型文件验证
│   └── skill.md
```

### 6.3 每个 Skill 的结构

```yaml
---
name: skill-name
description: 一句话描述这个 skill 做什么
version: 1.0.0
---
```

正文包含：
- **使用方式**：触发关键词
- **流程步骤**：按顺序执行，不要跳过
- **输出格式**：标准化的产物模板
- **注意事项**：边界条件和常见问题

### 6.4 方法论要点

1. **先有流程，后有 Skill**：做一次，沉淀流程，再编码为 Skill
2. **步骤要严格**：用"不要跳过"约束 AI，保证质量
3. **产出可预期**：定义标准输出模板，每次结果格式一致
4. **版本管理**：Skill 文件纳入 Git，跟随项目演进

## 7. 第六步：记忆系统与跨会话持久化

### 7.1 目标

AI 会话会被压缩或结束，关键的用户偏好、项目上下文、业务知识需要持久保存。

### 7.2 记忆体系

```
.claude/projects/{project-hash}/memory/
├── MEMORY.md              # 索引文件（总是加载到上下文）
├── about-user.md          # 用户角色、偏好、知识背景
├── project-overview.md    # 项目状态、目标、进度
├── feedback-*.md          # 用户反馈的偏好（对/错）
└── reference-*.md         # 外部资源位置
```

### 7.3 记忆分类

| 类型 | 保存什么 | 何时保存 |
|------|----------|----------|
| **user** | 用户角色、知识水平、偏好 | 了解到用户信息时 |
| **feedback** | 用户的纠正和确认 | 用户说"不要这样""对就是这样"时 |
| **project** | 项目目标、当前任务、决策 | 了解到项目相关进展时 |
| **reference** | 外部系统位置、文档索引 | 了解资源位置时 |

### 7.4 方法论要点

1. **只记住机器无法推断的内容**：代码规范、文件路径等信息能从项目本身读取，不需要存记忆
2. **feedback 要记录"为什么"**：不仅记录"不要做什么"，还要记录原因，以便未来做判断
3. **记忆要维护**：信息变化时更新或删除过时记忆
4. **索引截断保护**：`MEMORY.md` 超过 200 行会被截断，保持每行简洁

## 8. 第七步：上下文窗口管理与会话拆分

### 8.1 目标

AI 的上下文窗口有容量上限。超过阈值后系统会**自动压缩历史对话**，导致关键信息丢失，产出质量断崖式下降。本步骤确保在窗口满载前主动拆分会话，保持每次产出质量稳定。

### 8.2 上下文满了会怎样

上下文压缩不是"优雅降级"，而是**静默破坏**：

| 后果 | 具体表现 | 真实案例 |
|------|----------|----------|
| **信息丢失** | 压缩后的摘要丢失中间讨论细节，AI "忘记"已确认的方案 | — |
| **重复劳动** | AI 重新读取已读过的文件，浪费 token 和时间 | 同一 HTML 文件被反复 Read 4-5 次 |
| **简单操作出错** | 正则转义混乱、改错文件位置、变量名混用 | 门户端改造时 Node.js 正则连续报错 |
| **产出质量下降** | 丢失约束条件，生成的代码偏离已确认的规范 | 编辑页表单字段与原始弹窗不一致 |

**根因**：AI 不"知道"自己丢掉了什么信息，它看到的只是压缩后的残缺上下文，但行为上不会主动告诉你"我忘了"。

### 8.3 CLAUDE.md 减负策略

`CLAUDE.md` 是**常驻上下文**（每次会话自动加载），必须精打细算：

**砍掉的内容（三类可删除）：**

| 类型 | 示例 | 为什么删 |
|------|------|----------|
| **通用知识** | 工作流图表、开发流程说明 | AI 训练数据已包含，不需每次重申 |
| **空占位** | `<!-- TODO: 补充命令 -->` | 零信息量，纯占 token |
| **冗余指令** | "遵循架构约束" + "阅读架构文档" 同时存在 | 前者已被后者隐含 |

**保留的内容（四类必须留）：**

| 类型 | 示例 | 为什么留 |
|------|------|----------|
| **项目定位** | 一句话说清项目是什么 | AI 需要知道自己在做什么 |
| **行为约束** | "提交信息使用中文" | 直接影响产出行为 |
| **文件索引** | "功能实现前阅读 docs/xxx.md" | 告诉 AI 去哪找详细信息 |
| **特殊约定** | "新增工作方法时同步更新项目工作法" | 项目特有的操作要求 |

> **效果**：本项目 CLAUDE.md 从 30 行压缩到 13 行（-57%），每次新会话节省约 200 token 的常驻开销，且关键指令更集中、不会稀释。

### 8.4 会话拆分策略

**拆分粒度**：以 `git commit` 为天然分界点，一个会话 = 一个 commit 的工作量。

| 任务规模 | 建议 | 示例 |
|----------|------|------|
| 1-2 个模块改造 | 单个会话 | 宿舍配置 + 报修配置编辑页 |
| 3-5 个模块改造 | 可一个会话，注意监控 | — |
| 8 个模块、30+ 处修改 | **必须拆分** | 门户端编辑改造（本次踩坑） |
| 验证步骤 | **独立会话** | `/validate-prototype` 遍历全文件消耗大 |

**拆分信号（出现任一就该收手）：**

1. 同一大文件被 AI 重复读取 **3-4 次**
2. 简单操作（正则、路径拼接）连续出错
3. 系统出现 `<system-reminder>` 上下文压缩提示
4. 对话超过 **15-20 轮**，或代码变更超过 **500 行**

**跨会话状态传递**：拆会话不丢进度，靠 [memory 系统](#7-第六步记忆系统与跨会话持久化) 胜任。

```
会话1: 完成模块A → commit → 更新memory进度
   │
   ▼ 新会话
会话2: 自动加载memory → 知道模块A完成 → 继续模块B
```

### 8.5 HTML/PPT 文件特别注意事项

**HTML 原型文件**（如 `行政通.html`）是三端合一的大文件（1000+ 行），是上下文消耗主力：

- **编辑命令优先用 grep/sed**，避免 Read 整个文件
- **批量替换用脚本**（Node/Perl），不走逐行 Edit
- **修改后验证**用 `/validate-prototype`，但验证单独开会话

**PPT 文件**（如 `项目工作法.pptx`）是二进制文件：

- AI 不能直接编辑 .pptx，需要人工更新
- .md 源文件修改后，PPT 需要手动同步导出
- 建议在 .md 稳定后统一导出，避免频繁重做

### 8.6 方法论要点

1. **CLAUDE.md 不是 README**：不介绍项目、不放流程图，只放操作指令
2. **commit 即分界**：每次 commit 后评估是否可以新开会话
3. **memory 是桥梁**：进度、决策、偏好存 memory，新对话自动继承
4. **监控质量信号**：AI 开始"犯低级错误"时，不是它变笨了，是上下文被截了
